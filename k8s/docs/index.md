# Native runtime releases

`release.nu` reads the generated Compose project and deploys the same application images for compute, Feldera, Conduit, Redis, transform, ticker, clock, blob services and the airlock. A native computation must select `DUCKSTREAM_ENGINE=feldera`; the adapter refuses snapshot execution. PostgreSQL, CRUD, authentication, Electric, Caddy and optional rendering remain the shared application stack. Metal reads no Compose project: its release runs `App.services` and `App.blobs` alone.

Compute state and publication transactions remain in PostgreSQL. The database enables durable WAL writes and provisions 128 replication slots and senders for per-table CDC. Feldera's embedded catalog, compiler and runner directories share a persistent volume at `/home/ubuntu/.feldera`. Compute's lake and blob storage receive volumes too. Redis uses AOF with synchronous fsync. Conduit stores connector positions in PostgreSQL instead of memory. Every added runtime deployment has one replica and a Recreate strategy: release replacement must not overlap CDC writers. This trades release availability for a single writer; node fencing and backups remain cluster responsibilities.

`App.runtimeStorage` sets each runtime volume's size (default `10Gi`). `App.runtimeResources` sets runtime requests and limits (default request `500m`/`1Gi`, limit `4`/`8Gi`); compiler-heavy applications need capacity planned from their real workloads. Stateful volumes survive a deployment replacement. Deleting the namespace or its claims destroys that protection.

The adapter replaces Compose database credentials and internal service tokens with Kubernetes Secret references. It signs the internal service JWT from the deployed PostgREST key through stdin and stores it in an application Secret. Compose database passwords and internal JWTs never enter rendered manifests. HTTP services needed by Caddy join Dapr; native CDC and data-plane connections use namespaced Service DNS. Network policies restrict pipeline ingress to the app and permit its database, DNS, mesh and telemetry connections.

## The airlock

An app that declares an effect gets mecha's airlock as two Deployments, each its compose bake target's image with everything baked in: `airlock`, the worker (Service `airlock`, 9997, the health port the ticker's `GET /healthz` wakes), and `airlock-mesh`, a daprd of its own carrying the effects' HTTPEndpoints, the wall and the breaker (Service `airlock-mesh`, 3500). Neither has Dapr's injector annotations, and the release's sidecar check skips both: a second daprd beside the airlock would be a door around its wall.

Two pods keep the two walls compose builds with two networks, so an app with effects needs `networkPolicy.enabled`, or its render fails. The airlock takes only the ticker's wake on 9997 and reaches only the database on 5432, `airlock-mesh` on 3500 and DNS; `airlock-mesh` takes only the airlock on 3500 and reaches only DNS, the declared origins' ports (443, or an origin's own) outside the private, shared and link-local ranges (a cloud's metadata server among them), and the blob plane's `rclone-s3` on 3900 where the app has one. DNS is kube-dns in `kube-system`, NodeLocal DNSCache at 169.254.20.10, or the metadata server's 169.254.169.254 where GKE's Cloud DNS answers there (on 53 alone, so its HTTP stays shut), never any address on 53. No other policy selects either pod: policies add up, and one more would reopen a wall. Under `networkPolicy.internet: "airlock"` the daprd is the app's one way out. One pod (worker and daprd together) was rejected: one network namespace leaves the airlock's `--allow-net` as the only wall.

The airlock connects as the database's owner, as in compose. Its `ORIGIN` is the release's door. Each variable an effect reads as a secret (compose's `${K:?…}`, or `${K:-simulator}`) is read before compose interpolates it, so neither a missing nor an operator's value reaches the manifests: every compose read of the release takes a stand-in for it, and the operator need not export it. A name another service of the project also reads (a reference to it, `$$` being no reference; the name passed through, as `environment: [K]`; or any `env_file`) is that service's, from the environment, and gets no stand-in on this machine: unset, the release fails naming the service. Cloud Build's compose takes a stand-in for every one, shared or not, since no build reads one: a service whose `build` reads an effect's secret, by reference or as an arg passed through by name, is refused, its image would carry it. The airlock reads nothing else from the environment but `DATABASE_URL` and `ORIGIN`, which the release sets; any other reference fails the release, and so does an `env_file` on the airlock, whose values compose would merge into the manifests. Each secret becomes a reference to the Secret `airlock.secrets.<K>` names, under the key `K`. A variable not named there fails the render; a Secret or key missing from the namespace fails the release before anything rolls.

A database built before the app's first effect gets Graphile Worker's schema and the airlock's ledger from `<app>-initdb`. Over an already-built database it runs the image's `*_graphile_worker.sql` once, in one transaction, when Graphile's schema is not there: the step is no replay (it inserts its first migration and creates its tables bare), and Graphile migrates its own schema at every worker start. `*_airlock.sql` is re-runnable, and is replayed with the other steps on every release, in one transaction, so a mecha upgrade's ledger reaches a built database. Container bridges and the AI gateway (`tsbifrost`) are still refused, and so is an airlock without its daprd. So are a tenant's release of an app with effects, which drops every NetworkPolicy and the walls with them, and a preview of one, whose airlock would perform real effects with the release's sinks' credentials.

Kind provisions the existing operator stack and local certificate. `--dry-run` prints manifests and `--snapshot` validates rendering without applying resources. These checks do not build images or prove a live cluster rollout. The release builds and pushes every selected runtime image, applies schema jobs before services, and waits up to fifteen minutes for native startup.
