## Problem Statement

Lovable, Bolt, v0, and Replit Agent have proven that "type a prompt, get a working app at a URL" is a multi-billion-dollar product category. Lovable alone is reportedly at ~$45M ARR and $1.8B valuation in early 2026. The category is real and growing.

But every entrant in this category has the same architectural shape: the LLM generates code in a wide, loosely-typed substrate (React + Node + arbitrary state management), and "did it work?" is determined at runtime by trial-and-error iteration. This creates two structural problems:

1. **Success ratio is bottlenecked by the LLM's ability to produce correct code in a huge state space.** Generated apps frequently don't run, require manual debugging, or hit production walls the LLM can't predict.
2. **Cost-per-working-app is high.** Each iteration round costs LLM tokens. Hosting costs accumulate continuously regardless of whether the user's app is actively used.

A platform with **(a) constraint-cascade architecture** (LLM generates schema-checked declarative configs that fail at eval time instead of runtime) **and (b) scale-to-zero runtime** (hosting cost collapses to ~$0 for idle apps) can deliver the same prompt-to-app UX with structurally better economics and higher success ratio.

That platform is Pronto.

## Demand Evidence

- **Lovable**: ~$45M ARR, $1.8B valuation, ~50%+ ARR growth rate. Buyer exists, pays, expands usage.
- **Bolt.new**: 1M+ users, growing fast.
- **v0.dev**: tightly integrated with Vercel hosting, large user base.
- **Replit Agent**: integrated into Replit's broader IDE play.
- **Three production-deployed apps** built by the founder using LLM+mecha+sayt+bayt with zero hand-written code. Iris (~/code/trash/guis/iris) is a full Next.js app with 130 source files, i18n, e2e tests, k8s, components, hooks. **The constraint-cascade thesis is validated for N=1 founder using own stack. Generalization to naive users is unvalidated and is the single highest-risk claim in this design (see Open Questions).**
- **Token-cost reduction observed empirically**: fewer regeneration rounds + smaller prompts vs. equivalent Lovable workloads. Magnitude TBD via formal benchmark (see Assignment).

## Status Quo

Lovable-shaped buyers today:
- Type prompts at Lovable/Bolt/v0/Replit Agent.
- Pay $20-50/mo for hosted demos.
- Hit walls when the generated app needs real backend (state, auth, integrations, scale).
- Either: (a) accept the limitation and live with the toy, (b) abandon the platform and go back to hand-coding, or (c) hire a developer to "make it real."

Technical solo founders (Pieter-Levels-style indie hackers) who would be Lovable's natural power users:
- Currently reject Lovable because the output isn't production-grade and they can't own/maintain it.
- Hand-author everything OR use partial AI assistance via Cursor/Copilot in their own codebase.
- Pay nothing to Lovable; Lovable's TAM excludes them today.

## Target User & Narrowest Wedge

They want prompt-speed iteration AND production ownership. Technical taste (they'll appreciate the architecture) but care about user-facing outcomes (a working app they can deploy).

Secondary and tertiary ICPs (engineering teams, regulated industries) are **explicitly out of scope for this design**. They appear as post-PMF expansion targets only — see Appendix A for the post-PMF map.

**Narrowest wedge:** Closed beta. 50-100 paying users in 6 months (revised from "3 months" after capacity review). ## Constraints

## COGS Math (Defended)

Source assumptions, written down so they can be challenged or revised as we learn:

**Per active paying user, per month:**

| Cost line | Pronto | Lovable (est.) | Pronto delta | Source / reasoning |
|---|---|---|---|---|
| LLM tokens | $3.50 | $9.00 | -$5.50 | Lovable users avg ~80 iterations/mo × ~12k tokens each at Sonnet pricing. Pronto thesis: 50% fewer iterations (constraint catches errors) + 30% smaller prompts (smaller schema surface) = 65% of Lovable's token bill. **Unvalidated until benchmark.** |
| Hosting (active apps) | $1.20 | $4.00 | -$2.80 | Cloud Run paid tier @ ~50k requests/mo per active app × $0.40/M requests + memory + egress. Supabase **paid tier** @ Pro $25/mo amortized across ~20 active users = $1.25/user. NATS JetStream self-hosted on 1 small VM amortized = ~$0.05/user. Lovable uses Vercel for previews + Supabase = higher per-user cost. |
| Hosting (idle apps) | $0.05 | $1.50 | -$1.45 | This is the structural moat: scale-to-zero means idle apps cost ~zero. Lovable's hosting accumulates whether the app is used or not. Per-user impact compounds as users accumulate idle "abandoned" projects. |
| Customer infra (auth, billing, observability) | $1.50 | $1.50 | $0 | Clerk + Stripe + Sentry; same for both. |
| Support amortization | $3.50 | $0.50 | +$3.00 | Pronto is novel substrate → high per-user support cost early. Founder time @ ~$100/hr loaded × ~30 min/user/mo at 50-200 user scale = $3.50/user. Compresses to ~$1 once docs, examples, and self-serve mature (post month 12). |
| **Total COGS** | **$9.75** | **$16.50** | **-$6.75/user/mo** | |

So the defensible COGS delta is **~$7/user/mo** at beta scale (50-200 users) and **~$9/user/mo** once support amortization compresses post-month-12.

At 1,000 paying users (post-support-compression): **$9K/mo = $108K/year** of structural margin advantage. Real but modest at small scale.
At 10,000 paying users: **$90K/mo = $1.08M/year** of structural margin advantage.
At 100,000 paying users: **$900K/mo = $10.8M/year**. This is the acquisition-leverage moat at scale.

(At beta scale 50-200 users, the per-user delta is only $7 and total annual advantage is $4K-17K. The moat materialises as you scale; during beta you're paying for the validation, not collecting the moat dividend.)

Sensitivity: if the LLM-token thesis only delivers 25% (not 65%) reduction, total advantage compresses to ~$4/user/mo. Still meaningful but the acquisition-leverage story weakens. Benchmark resolves this.

## Recommended Approach

**Approach A — Closed beta hosted, OSS as launch milestone.**

Rationale:
- A is a strict subset of B. By sequencing it, you reduce execution risk during the cash-poor phase without giving up the long-term defensibility story.
- Closed beta is the fastest empirical test of P2 (success-ratio generalization). If P2 fails for naive users, you learn it for the cost of beta infrastructure, not 12 months for the cost of OSS community + hosted.
- OSS launch in month 12-15 becomes a marketing event with paying-user testimonials behind it. Strong narrative.
- Lovable can't react fast enough during the quiet beta phase. **Caveat:** Lovable's track record is shipping features in weeks; constraint-cascade could be a 2-engineer-month addition once observed. The "quiet phase" matters more as a marketing-narrative head-start than as a literal moat. Treat the head-start as defensible only if you turn beta data into evangelism, not as an unrecoverable architectural advantage.

The product:
- `pronto.dev` hosted SaaS, web UX matching Lovable's prompt-to-app shape.
- Behind the scenes: LLM generates CUE constrained by mecha schemas; bayt emits Dockerfile/compose/skaffold/etc.; sayt orchestrates lifecycle.
- Generated apps deploy to scale-to-zero hosting (Cloud Run paid tier + Supabase Pro paid + self-hosted NATS on 1 small VM).
- Pricing: $19/mo Hobby (3 apps, scale-to-zero hosting), $49/mo Pro (unlimited apps, faster builds, priority support), enterprise tier later.
- Self-host: gated as "request access" during beta. Made public concurrent with OSS launch (month 12-15).

**Working-app-percentage rubric (used in the assignment benchmark):**

A generated app counts as "working" if and only if:
1. Compiles without manual code edits.
2. Deploys to a publicly-accessible URL within the platform's standard flow.
3. Passes 3 scripted user actions defined per prompt (e.g., for "build me a CRM" → create contact, search contact, edit contact).
4. Reports no runtime errors in the first 5 minutes of the scripted user-action sequence.
5. Has no visible UI breakage on a desktop Chrome viewport.

A prompt is "succeeded on first iteration" if all 5 criteria pass without re-prompting. "Succeeded after N iterations" allows up to N re-prompt rounds.

## Hosted Abuse Vector (Trust & Safety)

Hosting user-generated apps means inheriting their abuse surface. Plan:

- **Crypto mining / compute abuse**: Cloud Run CPU quotas per user-app + per-account billing caps. Hard limit at $5/mo per Hobby user-app on platform-paid compute; user-paid overage above.
- **Spam / phishing**: outbound mail blocked by default; opt-in SMTP requires verified account + content scanning.
- **Scraping / DDoS**: ingress rate limits per generated app (100 req/sec default), egress rate limits.
- **Malicious content**: generated HTML/JS scanned at build time for known malware signatures via VirusTotal API.
- **Account abuse**: payment-gated signup (no free tier compute beyond LLM generation). Stripe Radar handles card-level fraud.
- **Response budget**: 4 hours/week of founder time allocated to T&S during beta; outsourced to a contractor at month 6 if user volume justifies.

This list is not exhaustive; it's a starting plan to be refined. Real budget item: ~$200/mo for content scanning APIs + ~$100/mo for fraud detection.

## Kill Criteria

Explicit decision gates. If reached, stop, extend, or pivot:

- **Kill (stop entirely)**: benchmark shows <1.5x success-ratio advantage over Lovable AND <30% token-cost reduction. The thesis isn't real; further investment doesn't help.
- **Extend the benchmark (no-decision zone)**: benchmark shows 1.5x-2x success-ratio OR 30-50% token-cost reduction. Borderline. Run a second benchmark round with a different 20-prompt set (more complex apps) and add the 10-user naive usability test before committing to hosted infra. Two more weekends, not "ship the product."
- **Pivot to Approach C (internal-tools niche)**: at month 6, fewer than 25 paying beta users despite 200+ invites issued. The consumer-Lovable comparison isn't the right buyer; shift to engineering teams.
- **Add co-founder before continuing**: at month 3, if calendar slip is >30% relative to plan, the solo execution assumption is broken. Don't keep grinding; recruit before more infra spend.

**Naive-user usability test honest caveat**: 10 users × 3 prompts = 30 trials is statistically thin for a load-bearing gate. Treat it as directional, not definitive. If results are close to threshold, extend to n=30 users (90 trials) before committing — adds ~3 weeks but reduces false-positive risk. Budget for the larger sample if the borderline case materialises.

## The Assignment

**Run the A/B benchmark against Lovable. Two weekends, not one.**

You don't need a beta product. You need the benchmark protocol:

**Weekend 1 (rubric + prompt set):**
- Write the rubric (criteria 1-5 listed above in Recommended Approach).
- Curate 20 prompts representing real B2B SaaS app ideas. Mix of complexity levels (simple CRUD, multi-entity with relationships, requires auth, requires real-time updates).
- Document the prompts in a versioned file.
- Set up Lovable account + scripted-user-action harness.

**Weekend 2 (execution + measurement):**
- For each of the 20 prompts:
  - Run against Lovable. First-gen result + up to 3 iteration rounds. Measure: working-app-rate per round, tokens consumed, subjective code quality 1-10.
  - Manually prompt-against-mecha (you as a proxy for Pronto). Same protocol. Same measurements.
- Tabulate. Compute working-app-percentage by iteration round, token-cost-to-working-app, subjective quality.

Total time: ~30-40 hours over two weekends. Budget $200-500 for Lovable subscription + LLM API costs for the manual mecha session.

This is the single artifact that gates everything else. If the numbers come back >2x Pronto on success-ratio and >30% lower on token cost, you have a YC application that opens with a number. If they don't, you've saved yourself 12+ months. **The benchmark gate is also the most-leveraged early-stage decision in this design.**
