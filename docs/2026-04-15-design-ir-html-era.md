## Problem Statement

AI code generation is unconstrained. Claude can generate anything in any language for any architecture. The output space is infinite, so correctness is probabilistic. Every generated application must independently get deployment, data consistency, scaling, and infrastructure right.

Pronto constrains AI generation to a well-defined target: mecha for data, omnishell for UI, sayt for build/deploy. Within this target, entire categories of bugs — deployment drift, data inconsistency, infrastructure misconfiguration, scaling bugs, state management bugs — become structurally impossible. The constraint is the feature.

Pronto is a compiler in the structural sense: it has a source language (markdown), an intermediate representation (ir.html), and a target (mecha + omnishell + sayt). The parse step uses an LLM rather than a deterministic parser, which means the pipeline has probabilistic characteristics that traditional compilers do not. Determinism is recovered through CUE contract validation, executable JS test pairs, and structured output constraints.

## What Makes This Cool

1. **The Rust analogy is precise, not marketing.** Rust doesn't generate different machine code than C. It constrains what the programmer can express. Pronto doesn't generate different apps than Claude Code. It constrains what the LLM can target. The constraint eliminates bug categories.

2. **The target architecture already exists.** Mecha handles data (CDC, PGlite, PostgREST, browser-to-cloud scaling). Omnishell handles UI (config-driven layout, auth, forms-only mutations). Sayt handles the TDD loop (setup, build, test, launch, integrate, release, verify). Pronto is the authoring layer on top of proven infrastructure.

3. **The two-artifact model.** Intent.md (mutable, natural language) → ir.html (immutable, structured: markdown + CUE + JavaScript + HTML storyboards). The IR is both machine-parseable and human-reviewable in any browser. Drift detection is multi-modal and mostly deterministic.

4. **Browser to cloud in the same code path.** PGlite in the browser, Docker Compose on a laptop, managed services in production. The architecture scales by swapping components, not by rewriting code.

## The Target Architecture

Pronto does not invent its runtime. It compiles to three existing systems:

### Mecha (data layer)

Schema-driven backend that generates CRUD + CDC + real-time sync from entity definitions. Three data paths:

| Path | Latency | What it does |
|------|---------|-------------|
| **Offline** | <1ms | PGlite in browser, local reads/writes, no network |
| **CRUD** | ~100ms | Synchronous SQL reads and writes via PostgREST |
| **CDC** | >500ms | Asynchronous pipelines — enrichment, notifications, analytics |

Mecha scales vertically by swapping components: PGlite → PostgreSQL, MSW → real HTTP, local filesystem → S3. Same data paths, same CDC guarantees, same application logic.

**Current status:** Under active construction. Browser platform (PGlite, jq-wasm pipelines) is functional. Platform abstraction (`@mecha/collections`, `@mecha/client`) is designed but the unified packages haven't been created yet. Codegen targets the existing `@mecha/browser` API for v1.

### Omnishell (UI layer)

Config-driven application shell with sidebar/bottom-nav layout, pluggable authentication, and architectural lint rules. Every omnishell app follows the same patterns: single data path, forms-only mutations, reactive queries via ElectricSQL.

**Current status:** Working scaffold with routes, components, auth integration, layout library, ESLint rules, Playwright visual lint checks, Storybook stories, and a working Dockerfile/compose.yaml. Past the design phase but not yet battle-tested with real applications.

### Sayt (build/deploy layer)

Lifecycle tool providing uniform verbs across every environment:

| Verb | What it does |
|------|-------------|
| `setup` | Install toolchains |
| `build` | Compile code |
| `test` | Run unit tests |
| `launch` | Start the application |
| `integrate` | Run integration tests |
| `release` | Publish artifacts |
| `verify` | E2E tests |

Sayt pins all generated artifacts to exact versions. This gives Pronto an unusual property: the target is immutable while the source is mutable. Both are committed to git.

**Current status:** Most mature piece. Has releases, verbs, and a working lifecycle across multiple environments (browser, CLI, IDE, container, k8s, cloud).

## What Needs Design Work

The target architecture is built (or being built). What's missing is the compiler pipeline that takes markdown and produces artifacts for that target. Four problems need solving:

### 1. The ir.html format

The intermediate representation is a single HTML file containing six embedded languages:

| Language | Role | What it expresses |
|----------|------|-------------------|
| **Structured markdown** | Metadata | Which mecha component each function maps to, lifecycle stage, data path (offline/crud/cdc) |
| **CUE** | Type contracts | Input/output schemas, field constraints, validation rules. CUE can validate JSON directly. |
| **JavaScript** | Executable tests | I/O test pairs and property tests beyond what CUE's type system can express. These become the golden-file test suite for generated code. |
| **HTML storyboards** | Animated wireframes | Interactive state sequences with CSS transitions, explicit happy/unhappy paths. Each path doubles as a test scenario. Renders in any browser. |
| **Mermaid** | Data flow diagrams | User-initiated data flows through mecha components. Shows pipeline topology, data paths (offline/crud/cdc), and latency tiers. Each flow maps to a storyboard path and JS test. |
| **Bloblang/jq** | Pipeline mappings | Transform logic for CDC pipelines, generated from behavior descriptions + CUE contracts. Embedded as `<script type="text/bloblang" data-pipeline="...">`. |

The IR is **intentionally lossy**. It captures more structure than intent.md but less than the generated code. What the IR captures: entity names, field types and constraints, data path assignments, page layout structure, behavioral triggers, I/O contracts. What the IR does NOT capture: specific CSS classes, component library choices (shadcn vs custom), import paths, exact variable names, TypeScript generics, framework-specific wiring. These are codegen decisions, not IR decisions.

#### Embedding conventions (resolved)

```html
<!DOCTYPE html>
<html>
<head>
  <meta name="pronto-ir-version" content="1">
  <meta name="pronto-source" content="intent.md">
  <meta name="pronto-generated" content="2026-04-15T14:36:35Z">
</head>
<body>
  <section data-role="entity" data-name="Todo" data-path="offline">
    <!-- Structured markdown: metadata about this entity -->
  </section>

  <script type="text/cue" data-entity="Todo">
    // CUE type contract for this entity
  </script>

  <script type="text/javascript" data-entity="Todo" data-test="true">
    // JS I/O test pairs for this entity
  </script>

  <div data-storyboard="todo-list" data-page="true">
    <!-- Interactive storyboard: named states + CSS transitions + path sequences -->
  </div>

  <pre class="mermaid" data-flow="create-todo">
    <!-- Data flow: user-initiated action through mecha components -->
  </pre>
</body>
</html>
```

Version attribute (`pronto-ir-version`) enables forward compatibility: v1 codegen reads v1 IR only; version mismatch is a hard error.

Storyboards replace static SVG wireframes. Each component/page gets a `<div data-storyboard>` containing: named states as HTML/CSS frames (low-fidelity: system fonts, gray borders, no imagery), CSS transitions between states (`@keyframes`, `transition`), and a `<script data-paths>` defining happy/unhappy path sequences as named arrays of state names. The storyboard auto-plays in the browser, cycling through paths. Each path directly maps to a behavioral test scenario, unifying visual spec and test spec in one artifact.

What storyboards capture that static wireframes don't: animation cues (fade, slide, shake), loading/skeleton states, error states and recovery flows, empty states, success feedback timing. These are the things that consume most design-to-development handoff time.

### 2. The parse step (intent.md → ir.html)

Claude reads natural language markdown and produces structured ir.html. This is the probabilistic step. Determinism is recovered through:

- **CUE contract validation** via `cue eval` CLI (added to `mise.toml` / `.pkgx.yaml` toolchain). CUE in ir.html defines entity contracts. These are distinct from mecha's existing CUE templates (`tmpl.cue`). Codegen reads ir.html CUE and emits artifacts compatible with mecha's generation pipeline.
- **JS execution.** I/O test pairs must execute without errors.
- **Storyboard validation.** Each `<div data-storyboard>` must have at least one named state and one path. States referenced in paths must exist. CSS parses without errors.
- **Mermaid validation.** Each `<pre class="mermaid">` must parse as valid mermaid syntax. Node names in flows should reference entities defined in CUE contracts. Flows should map to storyboard paths by `data-flow` name.
- **Partial retry strategy.** Validate each section independently (CUE, JS, storyboards, mermaid). On failure, only re-invoke the LLM for the failing section with the error appended. Max 3 retries per section. Worst-case: ~12s (3 retries x 4s). Typical case: single pass, ~2-4s.
- **User-facing error messages** citing the offending intent.md section.

Semantic errors that pass structural validation but produce wrong behavior (e.g., "counter showing completed / total" mapped to a text field instead of a computed display) are caught by JS I/O pairs. This requires Claude to generate meaningful test cases, not just schema-conformant ones. A "test quality" heuristic (minimum N test pairs per entity, at least one negative test) can gate acceptance.

### 3. Codegen (ir.html → mecha/omnishell/sayt artifacts)

Reads the structured ir.html and emits files. Two categories of codegen:

**Structurally deterministic** (CUE → data layer): Given CUE contracts, the output is fully determined.

| ir.html section | Generated file | Format |
|-----------------|---------------|--------|
| CUE contracts | protobuf schemas | Entity definitions for `buf lint` breaking change detection |
| CUE contracts (via proto) | `schema.sql` | PGlite DDL (CREATE TABLE + CDC triggers from mermaid flows) |
| CUE contracts + md metadata | `lib/mecha.ts` | `bootPlatform()` + `createCollections()` with adapter pattern (proven in snapcards) |
| CUE contracts + md metadata | `routes.ts` | PostgREST route definitions |
| Mermaid flows | `pipelines.ts` | CDC pipeline config for `createMechaCollections()` — jq-wasm transforms, source/sink wiring |
| Mermaid flows | `flows.md` | Human-readable data flow documentation (auto-generated from mermaid) |

**Heuristic deterministic** (storyboards → UI layer): Deterministic given a fixed set of mapping rules, but the rules themselves encode design decisions. A storyboard with states "empty", "loading", "populated" maps to a TanStack Router page using `useLiveQuery` + `createFileRoute` with Suspense boundaries. A storyboard state named "form-open" maps to a Zod-validated form component. CSS transitions in the storyboard map to the component library's animation system.

| ir.html section | Generated file | Pattern |
|-----------------|---------------|---------|
| Storyboard + behavior md | `routes/todos.tsx` | `createFileRoute` + `useLiveQuery` from omnishell scaffold |
| Storyboard (form states) | `components/todo-form.tsx` | Zod schema + forms-only mutation + validation error states |
| Storyboard (counter state) | `components/todo-counter.tsx` | Computed display from live query |
| Storyboard paths | `tests/todo-flows.test.ts` | E2E flow tests: one test per named path (happy, unhappy) |
| JS I/O pairs | `tests/todo.test.ts` | Golden-file test suite |
| md metadata | `sayt.config.ts` | Build config + artifact pinning |

**Codegen validation gate:** After emitting files, run `tsc --noEmit` to verify TypeScript compiles. Feed type errors back for a single codegen retry before surfacing to the user.

**Dependency gate:** Codegen targets the existing `@mecha/browser` API directly for v1. If/when `@mecha/collections` and `@mecha/client` land, codegen is refactored to the unified platform API.

### 4. Sayt TDD loop integration

The compile cycle must plug into sayt's existing verb model:

| Sayt verb | Pronto behavior |
|-----------|----------------|
| `sayt build` | Invoke the Pronto compiler: intent.md → ir.html → generated code. Pin all artifacts. |
| `sayt test` | Extract JS I/O pairs from ir.html, run against generated code. Validate CUE contracts. |
| `sayt launch` | Start the generated app (PGlite browser, Docker Compose, or cloud). |
| `sayt integrate` | Full pipeline: compile + test + launch. Integration tests against running app. |

The TDD loop: edit intent.md → `sayt build` → `sayt test` (JS I/O pairs fail or pass) → iterate. The IR carries its own test suite, so the feedback loop is: change intent → regenerate IR → tests tell you if the generated code matches the new intent.

## Drift Detection

With ir.html as the single intermediate artifact, drift detection is multi-modal:

| Type | Mechanism | Deterministic? |
|------|-----------|---------------|
| **Structural** | CUE schema diff between ir.html versions | Yes |
| **Visual** | Storyboard state/path diff + browser screenshot comparison | Yes |
| **Behavioral** | Run JS I/O pairs against generated code | Yes |
| **Flow (visual)** | Storyboard path diff — added/removed/reordered states in happy/unhappy paths | Yes |
| **Flow (data)** | Mermaid topology diff — added/removed nodes or edges in data flow diagrams | Yes |

All five mechanisms are deterministic. No LLM-on-LLM verification needed. The storyboard paths add a new drift dimension: flow drift. If a path gains a new error state or the transition order changes, that's a meaningful design change visible in the text diff.

## Schema Evolution

All entities are also described as protocol buffers. `buf lint` enforces breaking change detection, preventing destructive schema evolution (field renames, column drops, type changes) before codegen runs. Full shift-left: schema breakage is caught at the IR level, not at the database level.

The codegen chain: CUE contracts (in ir.html) → protobuf schemas → `buf lint` (breaking change gate) → SQL DDL (from proto) → `createMechaCollections`. Protobuf field numbers provide stable identifiers that survive renames, giving the IR a durable symbol model.

## Compile Conflict Resolution

The LLM compiler is non-deterministic. Different model versions or prompts may produce different ir.html for the same intent.md. This is not a bug. It is a merge conflict resolution workflow.

When `sayt build` recompiles intent.md and the new ir.html differs from the pinned version:

```
intent.md (unchanged)
    │
    ▼ [recompile]
ir.html (new version differs from pinned)
    │
    ▼ [git diff detects change]
COMPILE CONFLICT
    │
    ▼ [resolution agent analyzes:]
    ├── previous ir.html (what was built before)
    ├── spec.md (human-readable description of previous build)
    ├── full app code (what's currently running)
    └── new ir.html (what Claude now proposes)
    │
    ▼ [suggests resolution options]
    ├── Accept new (improvement is real)
    ├── Keep old (change is regression)
    └── Merge (keep some sections, update others)
```

spec.md returns in this context, not as a compile artifact but as resolution context. It is auto-generated from ir.html when the user accepts a compile, providing a frozen description of "what was intended at the time." The resolution agent uses it alongside the previous ir.html and generated code to understand whether a compile diff is an improvement or a regression.

Implementation details (agent model choice, resolution UI, auto-accept rules) are deferred. The concept is: compile diffs are productive, not problematic. Model improvements surface as reviewable changes, not silent mutations.

## Escape Hatches

Deferred to v2. The ir.html format reserves section types for:
- **HTTP endpoints** (full escape) — any external service accessible via HTTP
- **WASM components** (sandboxed escape) — compute-intensive logic in a sandbox

These appear in the IR as markdown metadata sections with CUE contracts for their interfaces, but no storyboards or JS (since they're opaque to Pronto).

## Constraints

- Mecha browser (PGlite, CDC, jq-wasm pipelines) is under active construction.
- Mecha platform abstraction (`@mecha/collections`, `@mecha/client`) is designed but not yet created.
- The LLM compiler adds latency (~2-4s per compile, ~12s worst-case with retries) that traditional compilers don't have.
- CUE validation requires the `cue eval` CLI in the toolchain (`mise.toml` / `.pkgx.yaml`). CUE is already used in the monorepo for sayt validation and IDE task extraction.
- Sayt is the most mature piece and the least risky dependency.

## Premises

1. **The bottleneck in AI code generation is correctness, not capability.** Constraining the output space is more valuable than expanding model capabilities.
2. **A fixed target architecture (mecha+omnishell+sayt) can cover a large class of commercial applications:** CRUD apps, SaaS tools, dashboards, e-commerce, content management, workflow automation, internal tools, and admin panels. What it excludes (real-time collaboration, GPU compute, sub-100ms distributed state) is genuinely niche.
3. **The two-artifact model solves the verification problem.** Intent.md (mutable) → ir.html (immutable). Drift detection is multi-modal and deterministic: CUE structural diff, storyboard state/path diff, JS test execution.
4. **The target architecture is mature enough to be a compiler target soon.** Mecha is under active construction. Omnishell has a working scaffold. Sayt is stable. Pronto's timeline is gated on mecha stabilization.
5. **Distribution through sayt is sufficient.** Scaffolding mechanism TBD (new `sayt init` verb, `degit`, or manual clone). No hosted service, no separate IDE, no new ecosystem.

## Cross-Model Perspective

Codex provided an independent cold read:

**Coolest version not yet considered:** Pronto as a brownfield architecture compiler — reverse-compile existing TS/Go/Kotlin services into spec.md, show drift, progressively squeeze into the constrained architecture. (Verdict: compelling v3 feature, too hard for v1.)

**What reveals the real obsession:** "Constraining generation to an architecture where deployment drift, data inconsistency, and infrastructure misconfiguration cannot exist." The excitement is eliminating failure classes by narrowing the solution space.

```markdown
## Data

## Behavior
```

### ir.html (generated, immutable)

```html
<!DOCTYPE html>
<html>

  <meta name="pronto-ir-version" content="1">

  <title>Todo App — Pronto IR</title>

  <h2>Todo</h2>
  <p>Offline-first entity. PGlite storage, local reads/writes.</p>
  <p>Mecha target: <code>createMechaCollections</code> with schema DDL.</p>
</section>

<script type="text/cue" data-entity="Todo">
#Todo: {
  id:         string & =~"^[0-9a-f-]{36}$"  // uuid
  title:      string & strings.MinRunes(1)    // required
  done:       *false | bool                   // default: false
  created_at: string & time.Format(time.RFC3339)
}
</script>

<script type="text/javascript" data-entity="Todo" data-test="true">
// I/O test pairs: input → expected output
export const tests = [
  {
    name: "create todo sets created_at",
    input: { title: "Buy milk", done: false },
    validate: (output) => output.created_at !== undefined
      && new Date(output.created_at).getTime() > 0
  },

    name: "toggle done flips state",
    input: { id: "abc-123", done: false },
    action: "toggle_done",
    validate: (output) => output.done === true
  },
  {
    name: "title is required",
    input: { title: "", done: false },

</script>
```

## Phased Delivery

1. **Week 1:** ir.html format definition (HTML template with CUE/JS/storyboard sections). Parser skill that takes intent.md and produces validated ir.html. Golden-file tests: todo-app intent.md → expected ir.html. Validation pipeline (CUE parses, JS executes, storyboards have valid states/paths).
2. **Week 2:** Codegen for mecha (CUE contracts + md metadata → schema + migration + PostgREST routes). Codegen for omnishell (storyboard states + behavior md → page config + forms + animation cues). Test extraction (JS I/O pairs → golden-file tests, storyboard paths → E2E flow tests). PGlite browser runtime integration. End-to-end: intent.md → ir.html → generated code → running app (a browser page served by `bun dev` showing a todo list from PGlite with working create form, empty/loading/populated states, and validation error feedback).
3. **Week 3:** Multi-modal drift detection (CUE diff, storyboard state/path diff, JS test execution). Sayt integration (`sayt build` invokes compiler, pins artifacts; `sayt test` runs extracted tests). Sidebar editor prototype (edit intent.md from within the running omnishell app).

## Success Criteria

- The todo-app intent.md compiles to a running PGlite-backed app via the ir.html pipeline
- Changing intent.md produces a new ir.html with visible multi-modal diff (CUE structural, storyboard state/path, JS behavioral)
- The IR is inspectable: open `.pronto/ir.html` in a browser and see metadata, type contracts, test cases, and wireframes
- JS I/O pairs extracted from ir.html pass against the generated application code
- `sayt build` and `sayt test` work with the Pronto compiler
- Parser and codegen have independent test suites with golden-file tests
- (Post-v1) A second LLM can be substituted at the parse step with no codegen changes

## Open Questions

1. ~~**ir.html section conventions.**~~ Resolved: `<section data-role>` for markdown, `<script type="text/cue">` for contracts, `<script type="text/javascript" data-test>` for tests, `<div data-storyboard>` for animated wireframes with `<script data-paths>` for state sequences. Version via `<meta name="pronto-ir-version">`.
2. **Semantic errors beyond CUE validation.** Mitigated by JS I/O pairs with a minimum quality gate (N pairs per entity, at least one negative test). Residual risk: Claude generates shallow tests. Monitor and improve prompt over time.
3. **Mecha readiness.** Browser (PGlite) is the v1 target. Container (Docker Compose) and cloud (managed services) are gated on mecha platform abstraction landing.
4. **Storyboard complexity budget.** How many states and paths per component before the storyboard becomes unwieldy? A rough guide: 3-7 states per component, 2-4 paths. More complex flows should be decomposed into sub-components with their own storyboards.
5. **Escape hatch IR representation.** Deferred to v2. Will appear as `<section data-role="external-service">` with CUE interface contracts, no storyboards or JS.
